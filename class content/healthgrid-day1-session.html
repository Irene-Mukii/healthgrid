Section 01

Today's Class

What you're actually learning, and why it matters more than you think.

Today introduces the client-server model as lived experience. Not as a diagram. Not as a definition. You will build a request that leaves your browser, travels to a Python process, gets routed to an LLM, streams back token-by-token, and lands in your UI. By the end of today you will have felt this pipeline in your hands. That physical understanding doesn't come from reading.

The second thing you're learning is how to define machine identity through language. The system prompt you write for Priya today is the first real act of AI systems design you'll do. It's small. It's also the exact same skill that makes or breaks multi-agent simulations at scale.

Objective 1
Understand request/response flow
Next.js sends a message → FastAPI receives it → Anthropic SDK formats it → Claude responds → SSE streams it back. You should be able to trace every step of this in your head by end of day.
Objective 2
Write your first real system prompt
The Priya persona prompt is not throwaway work. It's the template for all 20+ agents. You are writing the specification for a machine character. Understand why each line exists.
Objective 3
Store conversation history correctly
Without conversation history, every message is the first. With it, Priya remembers what was said 5 messages ago. You'll implement this in Supabase and understand the shape of the data.
Objective 4
Run two services simultaneously
Two terminals. One Next.js dev server on port 3000. One FastAPI server on port 8000. Understanding this separation is the foundation of understanding distributed systems.
What NOT to worry about yet

Authentication. Don't touch Supabase auth today. You're using a hardcoded user ID. Styling. The UI can be ugly. It just needs to send and receive messages. Multiple agents. One agent. One conversation. Depth over breadth. LangGraph. Not today. Today is just raw LLM calls. LangGraph comes when you have something to orchestrate.

Common beginner misconceptions — kill these early

"The system prompt tells the AI who it is forever." No. The system prompt is sent fresh on every single API call. The LLM has zero persistent memory. You are constructing the illusion of memory by including history in each request. This is the most important thing to understand about all LLM applications.

"FastAPI and Next.js need to share a codebase." No. They are completely separate processes that communicate over HTTP. This is exactly the separation that makes your architecture scalable later.

"I need to understand everything in the generated code before running it." No. Run it first. Break it second. Understand it third. In that order.

The mental model to build today

Think of the LLM as a stateless function: f(system_prompt + conversation_history + new_message) → response. It always returns the same "type" of output given the same "type" of input. Your entire job as an AI systems engineer is designing what goes into that function and what you do with what comes out. Everything else — memory, orchestration, streaming — is infrastructure around that core idea.

Before writing any code: draw the schema on paper. What does a messages row look like? What identifies a conversation? What order do messages come out in? Answer these questions first. The data model is a decision — it shapes everything that builds on it. This is schema design. It matters.

The key insight about conversation history

The Anthropic API expects messages in this shape: [{role: "user", content: "..."}, {role: "assistant", content: "..."}, ...]. Your database needs to store exactly this. Your fetch function needs to return exactly this. When you figure out this alignment between your DB schema and the API format, you've understood something foundational about building LLM applications.

⚠
Streaming is the hardest part of today. Server-Sent Events (SSE) work differently from a normal fetch. The response doesn't arrive all at once — it arrives as a stream of chunks. Generated code here will work but you should read it carefully. If streaming breaks, you need to understand enough to debug it. The key concept: ReadableStream, reading chunks with a reader.read() loop, and decoding bytes to text. Spend 15 minutes understanding just this pattern — you'll use it everywhere in this project.

End goal: type a message, press send, watch Priya's response appear word by word. If this is working, Day 1 is a success. Don't add more features. Ship the commit. Document what you built.

Section 04

How to Read the Generated Codebase

Senior engineers inspect unfamiliar codebases in a specific order. Learn the method now.

The senior engineer's codebase reading order

Start at the edges (what enters and exits the system), then move to the core (what transforms the data in between). Never start in the middle. Never start by reading every file top to bottom. Map the system first, then read the details.

Read in this exact order

Step 1 · Read first
ARCHITECTURE.md and both READMEs

Before any code. These tell you what the engineer (or AI) thought the system was. Then look at the actual code and see if it matches. Divergences between documentation and code are the most common source of bugs. Ask yourself: does this README match what I asked for?

Step 2 · Read second
models/schemas.py + types/chat.ts

The data types. These tell you what the system believes the world looks like. A ChatRequest Pydantic model tells you exactly what the backend expects. The TypeScript types tell you exactly what the frontend sends. If these two align perfectly, the system is coherent. If they drift, you get runtime errors.

Ask: what is the shape of a message? What is the shape of a request? Write it down on paper. Don't just read it — draw it.

Step 3 · Read third
agents/priya.py

Read the system prompt that was generated for Priya. Does it match your intent? Is it the Priya you imagined? This is where you'll likely need to rewrite. Generated personas are generic. Your Priya has specific personality traits you defined earlier.

Look at build_messages(). Trace what happens: history list comes in → new message gets added → full array is returned. Can you follow this in one read? If not, add comments until you can.

Step 4 · Read fourth
routes/chat.py — the endpoint

Trace the execution path of one request. Line by line. What happens when a POST hits /api/chat? In your head, follow: request arrives → validated by Pydantic → history fetched from Supabase → messages built → Anthropic call made → response streamed back → messages saved. Can you describe every step? If any step is unclear, that's where a bug will hide.

Step 5 · Read fifth
lib/api.ts — the streaming client

This is the most complex client code today. Read the streaming fetch function carefully. Look for: how does it start reading the stream? What does it do with each chunk? How does it handle errors? How does it know when the stream is done? If you can answer all four, you understand streaming well enough to debug it.

The folder structure you asked for creates one of the most important engineering habits: separating concerns. Here's what each layer is responsible for and why it matters:

Red flags in generated code — look for these

main.py is huge. If main.py has business logic in it, the structure wasn't followed. API calls in components. If ChatWindow.tsx calls fetch() directly instead of using lib/api.ts, that's coupling that will hurt later. Hardcoded strings everywhere. If the backend URL appears in 3 places in the frontend, configuration isn't centralized. No comments on async. The Anthropic messages array format Critical Every LLM call in this project depends on getting this array shape right. Misunderstand it and you'll have broken conversations that look fine until they don't. Read docs.anthropic.com/messages exactly once, carefully. Write 3 example arrays by hand. That's it.

You need a mental model, not memorized syntax. Read "Python async explained in 5 minutes" (search it). Understand: event loop, coroutine, what await yields to. 15 minutes. Non-negotiable.

Priya's voice must be yours. Write it yourself. Then test it. Then iterate. This is a skill you're building for the whole project — 20 agents all need this treatment.

Section 06

Manual Testing Guide

How to validate a system you just built. This is the discipline that separates engineers from script kiddies.

The testing philosophy for today

Test each layer in isolation before connecting it to the next layer. Backend works? Then connect frontend. Supabase works? Then use it in the endpoint. The moment you try to test everything together as a first step, you lose the ability to know where an error came from.

Run these checks in order

  • Supabase table exists. Go to your Supabase project dashboard → Table Editor. Does the messages table exist with the right columns? Can you manually insert a row? Do this before starting the backend.
  • Backend starts without errors. Run uvicorn main:app --reload. Does it start? Any import errors? Any missing environment variables printed in red? Fix these before anything else.
  • FastAPI interactive docs work. Open localhost:8000/docs. Can you see the POST /api/chat endpoint? Can you send a test request from the browser UI and see a response? This proves the backend works without the frontend.
  • Test the Anthropic connection specifically. In FastAPI docs, send: {"conversation_id": "test-001", "message": "Hi Priya, what's happening in the sprint today?"}. Does Priya respond as Priya — not as a generic assistant? If she sounds generic, your system prompt isn't being sent.
  • Check Supabase after a message. After the API call in the docs, go to Supabase Table Editor. Do you see two new rows — one user message and one assistant message — in the messages table? If only one, your save-after-response logic isn't working.
  • Test conversation history persistence. Call the API twice with the same conversation_id. Does the second call's response reflect what was said in the first? If not, your history fetch isn't working or isn't being injected into the prompt.
  • Frontend renders without console errors. Run npm run dev. Open browser. Open DevTools (F12) → Console tab. Any red errors before you've done anything? Fix these before testing interactions.
  • Network tab — watch the request. DevTools → Network tab → send a message. Click the request to /api/chat. Check: Headers (is content-type correct?), Request body (does it have the right shape?), Response (do you see streaming chunks, or one big blob?). Streaming should show as EventStream or text/event-stream.
  • Priya's personality test. Have a 5-message conversation about a fake sprint blocker. Does she stay in character? Does she remember what you said 2 messages ago? Does she sound like an actual Scrum Master, not a chatbot? If not — your system prompt needs work.
  • Error state test. Stop the backend. Try sending a message from the frontend. Does the UI handle the error gracefully (error message shown) or does it just hang or crash silently? Error handling is not optional.
When something breaks — the debugging mindset

Step 1: Isolate the layer. Is the error in the frontend, the network, or the backend? Open Network tab. Is the request being sent? Did it get a response? What was the response status code? Step 2: Read the actual error message. Don't Google the error until you've read it twice. Most errors tell you exactly what's wrong. Step 3: Add a log at the failure point. Add a print() in Python or console.log() in JavaScript right before where you think it breaks. Verify your assumption about what's happening.

The single most useful debugging habit: When something doesn't work, don't change 3 things at once. Change one thing. Observe. Change one thing. Observe. The urge to "fix everything" at once is how debugging sessions turn into 4-hour nightmares.

Before you close your laptop, spend exactly 15 minutes writing the following. Not for anyone else — for your future self reading this in Week 6 when you've forgotten what Day 1 felt like.

  • Commit your code. Message: feat: day 1 — priya agent with supabase persistence and streaming chat UI. Even if it's imperfect. Especially if it's imperfect. The git history of a learning project is one of its most valuable artifacts.
  • Screenshot or record a Loom of Priya responding. 30 seconds. Show the streaming. Show the conversation history working (two messages that reference each other). This becomes your first portfolio artifact.
  • Write one paragraph: "What I actually understand now that I didn't this morning." Be specific. Not "I learned about async."
