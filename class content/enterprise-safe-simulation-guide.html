01

Product System Breakdown

Architecture

HealthGrid is a browser-based enterprise simulation platform. The user plays a software developer who has just joined MedCore Systems — a fictional company that builds and maintains a Hospital Management Information System (HMIS). The company already exists. The teams are already operating. The backlog already has history.

Critical design principle

The user is joining an ongoing enterprise, not founding one. This is what makes it realistic. Architecture exists. Tech debt exists. Priorities already have political weight. The simulation should enforce this feeling from the first login.

Core Systems Map

The platform has six major system layers that interact to produce the simulation experience. Understanding how they connect is critical before building any single piece.

Layer 1

Simulation Engine

The central time controller. Manages the PI clock (simulated days/sprints), triggers ceremony events, generates blockers, injects changing requirements, and orchestrates the overall narrative arc of the experience.

Layer 2

Agent Ensemble

20–30 AI personas operating as your coworkers. Scrum Master, Product Manager, Architect, QA Lead, Team Leads from dependency teams. Each has persistent memory, personality, and realistic agenda-driven behavior.

Layer 3

Enterprise Context Store

The persistent "world state" — all architectural docs, ADRs, sprint history, team OKRs, backlog items, dependencies. Agents and the simulation engine query this to stay grounded and consistent.

Layer 4

Communication Layer

The Slack-like interface, ticket system (Jira-like), PR review flows, and meeting transcripts. This is where most of the user's experience lives — reading, writing, responding.

Layer 5

Evaluation Engine

Tracks user behavior across the simulation. Did they ask the right questions? Communicate blockers early? Demonstrate ownership? Score against rubrics that match real enterprise interview criteria.

Layer 6

Codebase Context Layer

Simulated repository structure. Not a working compiler — rather, believable file trees, partial implementations, README stubs, and API contracts that agents can reference and discuss.

Codebase realism strategy

Do NOT build actual working microservices. Instead, generate a believable skeleton: directory trees, interface files (.cs), README stubs, broken/partial implementations, and API contracts. Agents hold this context in their memory store and reference it naturally in conversation ("The IPatientRepository interface is in the Core layer, but the implementation has a TODO on the search method").

The goal is that codebase discussions feel real, not that the code compiles.

How SAFe Gets Simulated

SAFe Framework

A real SAFe Program Increment is 8–12 weeks, containing 4–5 two-week sprints plus an Innovation & Planning (IP) sprint. For a simulation, you compress this to a 4-week compressed PI with 2 sprints of ~2 days of real-time each.

The Simulated PI Timeline

Time compression model

1 real-world hour = 1 simulated workday

A full PI experience takes about 8–10 hours of user engagement spread over days or weeks. The simulation progresses asynchronously — events and messages accumulate whether or not the user is active, creating a realistic "you came back Monday morning and have 12 Slack messages" experience.

Simulated Event What Happens How AI Generates It User Role
PI Planning (Day 0) 2-day planning event. Teams present features, identify dependencies, commit to objectives. PM Agent presents feature set. Architect Agent explains constraints. Other team leads surface their plans and conflicts. Fill out team PI objectives. Identify your sprint commitments. Ask questions in breakout.
Sprint 1 Planning Team selects stories from backlog for sprint. Estimates. Assigns. Scrum Master Agent facilitates. PM Agent clarifies requirements. Backend Agent volunteers for stories. Claim stories. Estimate. Flag concerns about dependencies.
Daily Standup 3-question check-in. Blockers surface here. Each agent posts their standup update. Blockers are injected at ~30% frequency. Write your standup. React to others' blockers. Offer or request help.
Backlog Refinement Grooming upcoming stories. Defining ACs, estimates. PM Agent presents stories. BA Agent asks clarification questions. Tech Lead Agent adds technical constraints. Ask clarifying questions. Point out technical considerations. Suggest story splits.
Scrum of Scrums Cross-team sync. Team representatives surface inter-team issues. Each team's "representative agent" attends. Auth Team blocker becomes visible here. Represent your team's status. Flag your dependencies on other teams.
Sprint Review Demo completed work to stakeholders. Incomplete work is discussed. Stakeholder Agents ask questions. PM Agent tallies velocity. Incomplete stories get scored. Demo your completed work. Explain any incomplete stories honestly.
Retrospective Team reflects on process. What went well? What to improve? Scrum Master Agent facilitates. Agents share candid feedback that reflects the events of the sprint. Give genuine process feedback. Recognize teammates. Identify personal improvement areas.
PI System Demo End of PI. All teams demo integrated features to leadership. CTO Agent and VP Product Agent attend. Ask about dependencies between team deliverables. Articulate what the team delivered vs. committed. Explain variance.
Inspect & Adapt PI retrospective + problem-solving workshop. Leadership Agents present PI metrics. Teams brainstorm process improvements. Participate in identifying systemic issues. Propose solutions.

The Four Key Enterprise Dynamics to Simulate

1. Cross-Team Dependency Hell

The Pharmacy Team needs a Billing API endpoint that hasn't been built yet. The Auth Team has a deployment freeze. The Reporting Team needs event schemas to be finalized before they can proceed.

Simulation mechanism: Dependency Graph Agent tracks which tickets are blocked by other teams. Blockers surface in standup, Scrum of Scrums, and direct Slack DMs.

2. Ownership vs. Team Work

The simulation tracks what the user personally owned (stories they claimed, PRs they opened, tickets they moved) vs. what the team did collectively. This is directly scored in the PI review.

Simulation mechanism: All user actions are tagged. The evaluation engine can generate a "STAR-format story" at the end: what did YOU do vs. what did the team do?

3. Changing Requirements Mid-Sprint

A compliance officer injects a new security requirement on Sprint Day 3. A hospital client escalates an emergency patch. A stakeholder reprioritizes the backlog during an active sprint.

Simulation mechanism: Event injector fires with probability curves. PM Agent negotiates with Scrum Master Agent about scope changes. User must react appropriately.

4. Production Incidents

"The patient registration endpoint is returning 500s for hospitals in the eastern region." The on-call rotation pulls in the user. War room Slack channel. Postmortem. Follow-up tickets.

Simulation mechanism: Incident Agent fires at random. DevOps Agent provides log snippets. User must communicate status, investigate (simulated), and write postmortem.

What a Developer Actually Owns in Enterprise SAFe

This is the insight the simulation must make visceral. Most developers in large orgs spend their time on these activities — not architecture design:

Understanding existing systems — reading docs, asking senior devs, navigating legacy code sections

Implementing scoped backlog items — stories that are 2–8 hours of actual work, inside defined boundaries

Coordinating with adjacent teams — "I need the BillingService.GetInvoice endpoint to return X field"

Writing and reviewing PRs — describing changes, responding to feedback, understanding others' changes

Updating ticket statuses — moving cards, adding comments, linking PRs to stories

Communicating blockers early — "I can't progress on HMIS-4421 until the Auth team merges their API changes"

Participating authentically in ceremonies — not just attending, but contributing substance

Asking architectural clarifications — "Should this validation logic live in the application layer or domain layer?"

Handling unexpected complexity — "The legacy patient code doesn't follow the same pattern as the newer services"

Recommended architecture

LangGraph as the simulation engine and orchestrator. Individual agents use direct LLM calls (Claude or GPT-4o) with system prompts defining their persona. Supabase for persistent state. Redis for the event bus. This combination is buildable by a beginner in weeks, not months.

Start with CrewAI for your first prototype (1 week), then graduate to LangGraph for the real implementation. The concepts transfer directly.

Agent Communication Patterns

Broadcast

An event fires → all relevant agents see it → each responds in their channel independently. Used for: standup time, sprint events, incident alerts.

Directed Message

One agent sends a message specifically to the user or another agent. Used for: PR review requests, blocker discussions, direct DMs.

Conversational Thread

User replies to an agent, agent maintains context and responds. Multi-turn. Used for: clarifying requirements, architectural discussions, blocker resolution.

Meeting Simulation

Multiple agents participate in sequence. Facilitator agent manages turns. Used for: sprint planning, retrospectives, PI planning.

Async Reaction

User action triggers delayed agent response (simulating real response time). Used for: PR review feedback arriving 2 hours later, blocker updates.

Supervisor Pattern

Orchestrator agent monitors simulation state → decides which agents to activate → manages narrative coherence. The "game master" layer.

04

Modern Tech Stack

Implementation

Every choice is optimized for a solo developer building fast. No over-engineering. No premature scaling. Ship something real in 8 weeks.

North star principle

If you can't explain why you need it in one sentence, you don't need it yet

The biggest beginner trap is choosing technology for what it could do at scale, not what you need right now. This stack is chosen for speed of learning + speed of shipping.

FE
Frontend: Next.js 14 (App Router)
next, typescript, tailwindcss, shadcn/ui
You're already using Next.js (per the HMIS stack). App Router + Server Components makes it easy to build the Slack-like interface. Shadcn/ui gives you professional UI components in minutes. TypeScript catches bugs before they waste your time.
BE
Backend: Python + FastAPI
fastapi, uvicorn, pydantic, langgraph
The AI/agent ecosystem is Python-first. LangGraph, LangChain, all vector DB SDKs — everything works best in Python. FastAPI is modern, fast, and has excellent async support for streaming AI responses. Don't use C# for the platform backend — use it only inside the simulated HMIS codebase context.
AI
LLM: Claude 3.5 Sonnet (primary) + GPT-4o (backup)
anthropic python SDK, openai SDK
Claude 3.5 Sonnet has excellent long-context reasoning for maintaining agent personas consistently. GPT-4o is a natural fallback. Avoid fine-tuning at this stage — prompt engineering with structured system prompts is sufficient and much faster to iterate.
DB
Database + Auth: Supabase
supabase, postgres, supabase auth, supabase realtime
One service gives you: PostgreSQL (for simulation state), Auth (user accounts), Realtime (for the Slack-like live updates), and file storage (for simulated documents). Supabase's free tier is generous. Their TypeScript SDK integrates perfectly with Next.js. This single choice eliminates 4 infrastructure decisions.
VDB
Vector Database: Supabase pgvector (start) → Pinecone (scale)
pgvector extension, openai embeddings
Supabase's pgvector extension gives you vector search inside your existing Postgres database. No extra service to manage. For agent episodic memory retrieval, this is sufficient for thousands of records. Only move to Pinecone if you're hitting performance limits at scale.
ORC
Agent Orchestration: LangGraph
langgraph, langchain-core, langchain-anthropic
LangGraph models the simulation as a state machine — perfect for a time-stepped simulation engine. Nodes are simulation states (sprint day, ceremony type). Edges are transitions. Each node can call agents, update state, emit events. The visualization tools help you debug complex flows.
RT
Realtime: Supabase Realtime + Server-Sent Events
supabase realtime, fastapi SSE (starlette)
Supabase Realtime handles broadcasting new messages to the frontend (the Slack-like live feed). FastAPI SSE handles streaming LLM responses token-by-token. No need for a separate WebSocket server. This combination is beginner-friendly and has good documentation.
VOICE
Voice (Phase 3): ElevenLabs + Whisper
elevenlabs API, openai whisper API
ElevenLabs gives each agent a unique voice personality. Whisper handles user speech-to-text. For meetings, you generate audio ahead-of-time (TTS of agent scripts) and stream them. This is Phase 3 — do NOT attempt this in your MVP. It's a significant complexity jump.
OBS
Observability: LangSmith + Sentry
langsmith, sentry-python, sentry nextjs
LangSmith traces every LLM call — you can see exactly what prompt was sent, what was returned, token costs, latency. Critical for debugging why an agent said something wrong. Sentry catches frontend and backend errors. Both have generous free tiers.
DEP
Deployment: Vercel (frontend) + Railway (backend)
vercel, railway, docker
Vercel deploys Next.js apps with zero configuration — it's made by the same team. Railway runs Python FastAPI with minimal setup, supports environment variables cleanly, and has a free tier. Both have GitHub integration for automatic deployments on push. You can have production running in an afternoon.

Build Order

The biggest mistake you can make is trying to build the full vision before validating the core experience. The core experience is: talking to AI coworkers feels real. That's what you prove first.

The MVP question

What is the smallest thing that would make someone say "wow, that actually feels like working at a company"? That's your MVP. Everything else is polish or features.

Answer: A working standup with 4 AI coworkers + a simulated sprint board where you can move tickets. That's it.

Risks & Reality Check

Honesty

This is an ambitious project. Here is the honest assessment of where it gets hard and where most people quit. Knowing these in advance is your advantage.

Risk
Impact
Mitigation
Agent personality drift
After long conversations, agents start losing their character and sound generic. This breaks immersion entirely.
H
Inject persona reminder into every system prompt. Summarize long contexts rather than truncating. Test agents with 20+ turn conversations before shipping.
LLM cost spiraling
20 agents generating responses across a full PI simulation could cost $50–200 per user session at full context length.
H
Cache common agent responses. Use Claude Haiku for background agents, Sonnet only for primary interactions. Implement token budgets per session. Test real costs early.
Simulation coherence breaks down
Agents start contradicting each other about facts ("the Billing API is ready" / "the Billing API is blocked"). Immersion shatters.
H
Single source of truth: all factual state (API status, blocker status, story status) lives in Supabase, not in agent memories. Agents query state before making claims. This is your most important architectural rule.
Meeting simulation feeling unnatural
AI-generated meetings sound like they were generated by AI. The cadence is off, nobody interrupts, everything is too polished.
M
Add explicit personality friction to prompts: "Ravi tends to interrupt. Alex over-explains. Marcus is skeptical of new features." Add realistic imperfections: typos, unfinished sentences, "let me circle back on that." Study real meeting transcripts.
LangGraph complexity creep
LangGraph graphs become very complex fast. Debugging a failing state transition at simulation day 7 is non-trivial.
M
Keep the state machine as simple as possible for as long as possible. Use LangSmith for tracing. Draw the graph before implementing. Add nodes incrementally — never try to build the whole thing at once.
Scope explosion
You will want to add voice, mobile, 50 agents, real code execution, real GitHub integration... this kills solo projects.
H
Write your MVP scope on a sticky note and look at it before opening your laptop every day. Every new idea goes on a "v2 list." The v2 list should never gate v1 shipping.
User experience design underestimated
The simulation is technically impressive but users don't know what they're supposed to do. Onboarding is hard.
M
Build onboarding first, not last. Day 0 of the simulation = orientation meeting with Priya. She explains the team, what your first week looks like, and what's expected of you. Explicit guidance inside the simulation.
Voice agents are genuinely complex
Real-time voice with multiple agents, latency, turn-taking, interruption handling — this is a month-long feature at minimum. Not a week.
L
Treat voice as v1.1 or v2. For meetings, pre-generate audio (TTS of a scripted exchange) rather than real-time voice. Much simpler. Still impressive.
The #1 thing that will kill this project

Spending 3 weeks trying to make one agent "perfect" instead of having 5 agents that are "good enough." The simulation's value comes from the ensemble — from the combination of agents interacting with each other and with you. One perfect agent is just a chatbot.

The Three Rules to Finish This

Rule 1: Ship Ugly

Your first deployed version should be embarrassing. That's correct. Embarrassing and deployed beats perfect and local by infinity.

Rule 2: Fake Aggressively

Every feature that can be hardcoded or faked without breaking the core experience — fake it. Real automation comes in the next version, after you know the design is right.

Rule 3: Use the Product

Run through the simulation yourself every week. Not to test it — to experience it as a user. The moment it feels boring, your users will feel it too. That's your signal to redesign.
